# AI 对话体验优化计划

> 文档版本：v0.2
> 创建日期：2026-08-18
> 最近更新：2026-08-18
> 适用范围：`forge-plugin-ai`（后端）+ `forge-admin-ui/src/views/ai`（前端）
> 优化重心：**对话 / 使用体验**，不包含成本治理、能力开放平台、低代码应用等其它 AI 域

---

## 一、背景与目标

当前系统 AI 能力已经比较完整，供应商管理、模型管理、普通对话、Agent 引擎、知识库、多模态输入都已经具备，但在“能用”到“好用”之间还有明显断层。最主要的问题不是模型能力不足，而是对话链路的体验不够稳定，历史消息承载不够完整，错误与中断没有形成闭环，长会话的渲染性能也不够好。

这次优化的目标很明确：把 AI 对话页做成一个真正可交付的工作台，而不是只把接口打通。

目标分成四层：

1. 让 Agent 对话具备稳定的流式体验，能清楚看见连接、输出、暂停、恢复和结束。
2. 让历史消息可回放，能看见正文、思考过程、工具调用、附件和状态变化。
3. 让错误和 HITL 成为完整闭环，而不是“发生了，但用户看不懂，也接不回去”。
4. 让会话管理、消息操作、性能和埋点进入可持续迭代的状态。

本计划只做“对话体验”本身。协议统一、普通 chat/generate 的全链路重构、其它页面的统一改造，都作为后续独立专项，不在阶段一里展开。

## 二、现状盘点

### 2.1 已确认的代码事实

下面这些是当前代码里已经能直接确认的事实，不是推测。

| 项目 | 现状 |
|------|------|
| Agent 引擎入口 | `AgentEngineController` 提供 `/ai/engine/stream` 和 `/ai/engine/resume`，两者都返回 `Flux<ServerSentEvent<String>>`。 |
| Agent 引擎执行方式 | `ReactLoop.callModel()` 仍然使用 `chatModel.call(prompt)`，也就是同步整段返回，不是 token 级流式。 |
| Agent 文本下发 | `ReactLoop` 当前把模型输出打成单个 `TEXT_BLOCK_DELTA` 事件下发，不是按 token 或 chunk 逐步输出。 |
| 普通对话流式 | `AiClientImpl.stream()` 已经是 Spring AI 流式链路，`AiChatController.chatStream` 也是 token 级输出。 |
| 普通对话错误处理 | 普通链路的 `onErrorResume` 会把 fallback JSON 混进消息流，前端如果按纯文本拼接，会出现内容污染。 |
| 会话实体 | `AiChatSession` 已经有 `sessionName`、`status`、`metadata`、`createTime`、`updateTime`，支持做会话管理。 |
| 消息实体 | `AiChatRecord` 目前只有 `tenantId/userId/agentCode/sessionId/role/content/tokenUsage/createTime`，还缺 `updateTime`、`status`、结构化字段。 |
| 历史记忆 | `DbChatMemory.get()` 只取最近 20 条消息，无法承担“从某条消息之前截上下文”的重发逻辑。 |
| 会话服务 | `AiChatSessionService.getOrCreate()` 已经具备幂等创建能力，`listByUser()`、`deleteSession()`、`touchSession()` 也都已经存在。 |
| 会话页面 | 前端 Agent 对话页目前主要集中在 `agent-chat.vue`，消息回放、HITL、流式渲染都堆在一起。 |
| SSE 解析 | `forge-admin-ui/src/api/ai.js` 里已经有手写 SSE 读取逻辑，`engineResume()` 目前却不是 SSE 方式。 |

### 2.2 当前体验问题

1. Agent 输出不是实时渐进式的，长回复要等到模型完整结束后才开始看见正文。
2. 历史消息回放不完整，assistant 的思考、工具调用、附件语义都回不来。
3. 错误没有形成统一展示，用户看不到明确的失败态，也没有稳定的重试入口。
4. HITL 确认后，恢复返回的流没有接到原消息上，确认后的输出会断掉。
5. 新会话和会话标题管理还比较粗，刷新、重命名、筛选、分页都不完整。
6. 流式渲染是全量重排，长消息下会很卡。
7. 结构化数据不足，后续做回放、分析、埋点时只能继续在字符串里打补丁。

### 2.3 涉及范围

- 前端：`forge-admin-ui/src/views/ai/agent-chat.vue`、`forge-admin-ui/src/api/ai.js`、`forge-admin-ui/src/views/ai/session.vue` 及其配套组件
- 后端：`forge-plugin-ai` 下的 `agent/engine`、`chat`、`session`、`client`、`memory` 相关模块
- 数据库：`ai_chat_record`、新增的对话工具调用表、会话相关迁移

## 三、问题清单

### P0

1. **Agent 对话不是实时流式体验**

   当前 `ReactLoop` 通过 `chatModel.call()` 取得完整结果后，再一次性发出文本事件，用户看不到逐步输出。

2. **HITL 恢复后无法接回原消息**

   `/ai/engine/resume` 虽然后端已经返回 SSE，但前端 `engineResume()` 仍然按普通请求处理，恢复后的流被丢掉。

3. **错误没有统一落点**

   当前错误态在不同链路里表现不一致，有的被忽略，有的被混进正文，用户很难区分“模型回答”与“系统错误”。

4. **历史消息不能完整回放**

   `ai_chat_record` 还没有结构化字段，历史只靠 `content` 兜底，思考块、工具调用、附件、状态都无法稳定恢复。

5. **新会话和会话标题管理不完整**

   新建会话、重命名、分页、搜索、Agent 过滤都不够完整，侧栏更像临时列表，不像正式会话管理。

6. **长消息渲染卡顿**

   前端流式期间频繁全量 Markdown 重渲染，消息越长越卡。

### P1

7. 消息缺少复制、重试、重生成、编辑等基础操作。
8. 输入区缺少附件/图片接入，虽然后端已经支持 `imageFileIds`。
9. 对话页缺少明确的连接状态、等待状态、完成状态提示。
10. 会话列表缺少分页、滚动加载和按 Agent 过滤。
11. 没有统一的用量、耗时、首 token 等体验指标展示。
12. 空对话没有引导，用户首次进入不知道怎么开始。
13. 停止生成后缺少继续生成入口，用户只能重开一轮。

### P2

14. 结构化消息模型不完整，后续回放与分析成本高。
15. SSE 解析和消息渲染逻辑分散在页面里，复用性差。
16. `agent-chat.vue`、`agent.vue` 这类页面偏大，后续维护成本高。
17. 缺少稳定的对话体验埋点，无法做前后对比验证。

## 四、已锁定的设计决策

下面这些决策已经定死，后续实现按这个来，不再回头改方向。

### 4.1 协议策略

1. **统一事件协议**，不再做双轨制。
2. **协议的主骨架先按 Agent 事件定义**，因为 Agent 链路事件最完整，适合当统一规范的起点。
3. **状态统一进入协议**，至少包括 `connected`、`streaming`、`waiting_confirm`、`error`、`done`。
4. **一条消息一行事件**，不要把多个阶段混进一条记录里。
5. **正文只放最终回复内容**，思考过程和工具调用单独结构化承载，不再继续拼在正文字符串里。
6. **工具调用单独加表**，放在消息下方，按 `record_id` 关联 assistant 消息。
7. **一次工具调用一行**，便于回放、筛选和审计。
8. **HITL 先写 `waiting_confirm`，再更新同一行**，不要新开一条状态记录。
9. **resume 输出接回原 assistant 消息**，不是再开一条新的助手消息。
10. **提问时先建 assistant 行，状态先记为 `streaming`**，后续按阶段更新到 `done`、`error` 或 `aborted`。

### 4.2 落库策略

11. **新建统一的会话持久化服务，但不要再搞 Service 互相注入的编排链**。
12. **会话编排放在 Controller / 编排层**，按事件触发写库，复用现有 Service 能力。
13. **终止信号统一收口**，至少区分 `done`、`aborted`、`error`。
14. **重试时软删旧 error 行，再新建一条**，保持消息序列可读。
15. **重新生成沿用同一套软删 + 新建逻辑**，不要再额外发明一套分支。
16. **重发时显式构造上下文**，只截到该轮提问之前，不能把后续消息带进去。
17. **重发路径不依赖自动 memory 回放**，而是明确组装上下文，避免“取最近 N 条”这种不可控截断。
18. **附件存用户消息行**，不是挂在 assistant 上。
19. **token_usage 保留**，同时补充 usage JSON，后续分析更完整。
20. **Flyway 从 `V1.0.124` 起新增迁移**，不修改已执行脚本。
21. **一个脚本同时完成加列 + 建表**，迁移保持幂等。

### 4.3 前端策略

22. **流式期间做增量 Markdown 渲染**，但不要每个 chunk 都全量重算。
23. **采用节流，只重渲染最后一个块**，保留实时性，也避免重排抖动。
24. **消息内联错误块 + 重试按钮**，不要把错误从对话里踢出去。
25. **历史回放优先读结构化字段**，旧消息继续用 `content` 兼容兜底。
26. **`engineResume` 改成 SSE 读取**，继续流必须接回原消息。
27. **附件缩略图挂在用户消息上**，视觉上和文本保持一致。
28. **会话列表做分页和上滑加载**，长列表不要一次性全灌。

### 4.4 会话管理策略

29. **新增 `POST /ai/session` 显式创建接口**，会话创建即落库。
30. **创建时绑定当前 Agent**，一个会话与一个 Agent 关联，减少上下文歧义。
31. **新增 `PUT /ai/session/{id}` 重命名接口**，前端不再自己截标题。
32. **新增分页 + 关键词搜索 + Agent 过滤**，让左侧会话列表真正可用。
33. **前端新增 Agent 选择入口和顶部过滤器**，配合后端过滤条件使用。
34. **去掉前端截标题重复逻辑**，标题只以服务端规则为准。

### 4.5 分期策略

35. **阶段一只落地 Agent 引擎链路**，不把普通 `chat/stream`、`generate/stream` 一起大改。
36. **普通对话和大屏链路的协议统一放到后续独立专项**，不要和阶段一混在一起。
37. **阶段一目标是先把 Agent 对话做稳做顺**，后续再统一其它链路。

## 五、分阶段路线图

### 阶段一：Agent 对话主链路落地

阶段一只做 Agent 引擎链路，目标是先把“实时输出、恢复接续、消息落库、历史回放、错误可见”这五件事做通。

这一阶段拆成三个变更包：后端、前端、会话管理。三者可以并行推进，但验收要按顺序串起来。

#### 5.1 变更 A：后端链路和消息落库

**目标**：把 Agent 对话从“只返回结果”升级成“可追踪、可恢复、可结构化回放”的事件链。

**范围**：`ReactLoop`、`AgentEngineService`、`AgentEngineController`、`ai_chat_record`、工具调用表、会话编排写库逻辑、最小埋点。

**具体任务**：

1. **保留 `ReactLoop` 的 `Sinks` 结构**

   继续用 `Sinks.many().multicast().onBackpressureBuffer()` 承载事件流，不改成一次性同步返回。

2. **把 `callModel()` 改成流式消费**

   底层从 `chatModel.call(prompt)` 改成 `chatModel.stream(prompt)`，在内部阻塞消费流式 chunk，再逐块发出事件。

3. **拆分文本阶段事件**

   文本输出按 `TEXT_BLOCK_START`、`TEXT_BLOCK_DELTA`、`TEXT_BLOCK_END` 走，不再把完整文本压成一个 delta。

4. **思考块单独落库**

   通过模型 metadata 或解析逻辑拿到 reasoning 内容，落到独立字段，不再继续混在正文里。

5. **工具调用单独落表**

   新增工具调用表，按 assistant 消息的 `record_id` 关联，每次工具调用一行，记录工具名、参数、状态、结果摘要和时间。

6. **HITL 先置 `waiting_confirm` 再更新同一行**

   遇到需要人工确认时，先把当前 assistant 消息状态改为 `waiting_confirm`，记录 `interruptId`，确认后继续写回同一条消息。

7. **终止状态统一收口**

   正常结束写 `done`，人为中止写 `aborted`，异常写 `error`，不要再让状态散落在多个字段或多个事件里。

8. **重试和重新生成走统一写法**

   对 error 消息做软删，再新建一条新的 assistant 记录，保证消息序列干净。

9. **重发时显式构造上下文**

   不依赖 `DbChatMemory` 的最近 N 条回放，而是按当前轮提问点截取上下文，避免后续消息污染重发结果。

10. **最小埋点先落地**

    先接入最小的对话埋点，复用现有 `AiModelInvocationRecorder` 相关能力，至少记录发送、首 token、完成、错误、中断和总耗时。

11. **Flyway 新增迁移脚本**

    使用 `V1.0.124__enhance_ai_chat_message_structure.sql` 之类的新增脚本完成字段扩展和新表创建，脚本保持幂等，避免重复执行出错。

**建议落库结构**：

- `ai_chat_record`
  - 继续保留现有正文字段和 `token_usage`
  - 新增 `status`
  - 新增 `reasoning` / `usage_json` / `attachment_json` 之类的结构化字段
  - 补齐 `update_time`
- `ai_chat_message_tool_call`
  - `record_id`
  - `tool_name`
  - `tool_args_json`
  - `tool_result_json`
  - `status`
  - `create_time` / `update_time`

**验收标准**：

- Agent 对话能逐块输出，不再等完整结果一次性出现。
- `resume` 后的流能继续接回原 assistant 消息。
- 消息、思考、工具调用都能落库并回放。
- 错误、确认、结束状态在数据库和前端上表现一致。

#### 5.2 变更 B：前端流式渲染和消息回放

**目标**：让前端真正把事件流接住，并且在长对话下仍然保持顺滑。

**范围**：`forge-admin-ui/src/views/ai/agent-chat.vue`、`forge-admin-ui/src/api/ai.js`、消息渲染组件、错误块和重试入口。

**具体任务**：

1. **统一 SSE 解析器入口**

   把 Agent 引擎的 SSE 读取整理成统一的事件解析器，明确区分 `event:` 和 `data:`，前端只消费结构化事件对象。

2. **`engineResume` 改为 SSE 接流**

   现在的 `request.post()` 必须改掉，恢复接口要像主流接口一样走 SSE，恢复结果接回原 assistant 消息。

3. **流式期间增量 Markdown 渲染**

   采用节流策略，只对最后一个块做快速重算，前面的稳定内容不再反复全量 `marked.parse`。

4. **历史消息回放优先结构化字段**

   历史渲染先读 `reasoning`、`toolCalls`、`attachments`、`status` 等字段，旧数据没有这些字段时，再回退到 `content` 解析。

5. **内联错误块 + 重试按钮**

   错误直接落在消息流里，提供“重试”而不是把错误弹到消息外面。

6. **附件缩略图接入用户消息**

   用户消息展示附件预览，和文本气泡在同一条消息里，不单独拆出去。

7. **滚动与回放策略调整**

   长会话只加载最近消息，向上滚动时继续拉更早消息，避免一次性把所有历史撑进 DOM。

8. **消息操作入口预留**

   复制、重新生成、编辑重发、删除单条等动作先在 UI 上预留标准位置，方便阶段二继续补齐。

**验收标准**：

- 流式输出能持续刷新，但不会频繁卡顿。
- 历史消息能看见结构化内容，旧消息也不会丢。
- `resume` 后的输出能接回原消息，不会“确认后断流”。
- 错误态明确，用户能直接点重试。

#### 5.3 变更 C：会话管理和入口整理

**目标**：让会话列表从“临时列表”升级成正式管理入口。

**范围**：会话创建、重命名、分页、搜索、Agent 过滤、侧栏交互。

**具体任务**：

1. **新增 `POST /ai/session`**

   新会话显式创建并落库，不再只是前端本地 `unshift`。

2. **创建即绑定 Agent**

   一个会话对应一个 Agent，后续消息默认沿用这个上下文。

3. **新增 `PUT /ai/session/{id}` 重命名**

   标题由后端统一生成和维护，前端不再重复做截断逻辑。

4. **新增分页和搜索**

   会话列表按页返回，支持关键词和 AgentCode 过滤。

5. **增加顶部过滤器**

   前端提供当前 Agent / 全部会话等过滤入口，和后端分页参数对齐。

6. **侧栏滚动加载**

   会话侧栏只加载必要数据，避免一次性把全部历史都挂在页面里。

**验收标准**：

- 新会话刷新后仍然存在。
- 会话能重命名、能搜索、能按 Agent 筛选。
- 长列表不会一次性塞满页面。

#### 5.4 阶段一总验收

阶段一完成后，Agent 对话页至少达到以下状态：

- 能看到连续的流式输出。
- 能在确认后接回输出。
- 能回放历史中的正文、思考和工具调用。
- 能明确看到错误和重试入口。
- 新会话不会刷新丢失。
- 长消息不会明显卡死页面。

---

### 阶段二：消息与会话交互增强

阶段二在阶段一稳定后再做，目标是把对话页补成一个完整的工作台。

**范围**：复制、编辑、重试、重新生成、删除单条、停止后继续、消息状态展示、会话管理增强。

**建议项**：

1. 消息复制，保留 Markdown 原文。
2. 消息编辑后重发，生成新一轮 assistant 回复。
3. 重生成和重试共用一套消息操作逻辑。
4. 单条消息删除采用软删，不破坏历史序列。
5. 停止生成后保留已输出内容，允许继续生成。
6. 展示 token 用量、耗时、状态标签和连接状态。
7. 左侧会话列表支持更完整的筛选和管理动作。

**阶段二验收标准**：

- 消息操作完整。
- 会话列表可管理。
- 用户能清楚知道当前生成状态和消耗情况。

---

### 阶段三：输入能力与上下文能力

阶段三做输入侧增强和上下文体验增强，重点是“更像一个完整 AI 助手”。

**范围**：附件、图片、空状态、推荐问题、上下文管理、HITL 体验细化。

**建议项**：

1. 输入区支持附件和图片上传，接入 `imageFileIds`。
2. 空状态展示欢迎语和推荐问题。
3. 长会话做上下文裁剪或摘要，避免直接爆上下文窗口。
4. HITL 恢复增加倒计时和等待态，明确用户现在要做什么。

**阶段三验收标准**：

- 能上传图片并带入对话。
- 空会话有引导。
- 长会话上下文可控。
- HITL 的等待和恢复体验完整。

---

### 阶段四：工程化与度量

阶段四关注可持续演进，重点不是“再做一个功能”，而是把这条链路变得更容易维护和验证。

**范围**：组件拆分、SSE 工具化、埋点、体验指标、复用。

**建议项**：

1. 把 `agent-chat.vue` 拆成消息列表、消息气泡、思考块、工具卡片、输入区、会话侧栏等子组件。
2. 把 SSE 读取从页面里抽出来，做成可复用工具。
3. 接入对话体验埋点，形成发送、首 token、完成、错误、中断的基线。
4. 后台页面增加体验指标视图，便于观察优化前后差异。

**阶段四验收标准**：

- 页面组件化程度明显提高。
- SSE 处理可复用。
- 体验指标可追踪。
- 后续链路迁移时成本更低。

---

## 六、后续独立专项

下面这些内容不放进阶段一，后续单独开专项处理：

1. 普通 `chat/stream` 的全链路协议统一。
2. 大屏、低代码、其它 AI 页面对 SSE 协议的统一改造。
3. 旧的 fallback JSON 混流彻底清理。
4. 全站消息协议、状态协议和错误协议统一。

这部分不要和阶段一混在一起，否则改动面会被拉得过大。

---

## 七、风险点

1. **流式改造会影响时序**

   `ReactLoop` 从同步结果改成流式消费后，事件产生顺序、HITL 中断、工具执行回写都要重新校验。

2. **前端重渲染和滚动要一起设计**

   只做增量渲染不够，必须同时考虑用户上滑查看历史时的滚动锁定问题。

3. **历史兼容不能靠一次性回填**

   老数据先兼容读，后续有条件再做补录，不要把阶段一拖进大规模补数任务。

4. **不要在阶段一就碰所有消费端**

   协议统一后续再做，阶段一只服务 Agent 引擎，不要顺手把普通 chat/generate 全都拉进来。

5. **落库结构要先定，再写代码**

   `ai_chat_record`、工具调用表、状态字段、usage JSON 的结构要一次定清楚，避免后面不停补字段。

---

## 八、落地建议

1. 阶段一优先做后端结构和协议，再做前端回放与恢复，最后补会话管理入口。
2. 新增字段和新表全部走 Flyway，保持幂等，不修改已执行脚本。
3. 前端先把 SSE 解析和恢复接口打通，再做增量渲染和错误块，这样能尽快验证主链路。
4. 先把 Agent 引擎链路做稳，再做全局协议统一，别把两个问题绑成一个大改。
5. 第一轮交付后，先看真实使用反馈，再决定阶段二、三、四的优先级。

## 十、阶段一的最终判断标准

如果阶段一做完，用户应该能清楚感受到这几件事：

- 说话后立刻有反馈，不再长时间空等。
- 确认和恢复是连贯的，不会确认完就断。
- 历史记录不再只是几段正文，而是能看见完整对话轨迹。
- 错误不是悄悄吞掉，而是明确展示并支持重试。
- 会话是可管理的，而不是临时堆在侧边栏里。

这个状态达成后，再进入协议统一和其它页面的同步改造，顺序就比较稳。
