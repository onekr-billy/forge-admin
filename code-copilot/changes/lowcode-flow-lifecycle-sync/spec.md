# 低代码单据与审批流程生命周期同步 Spec

> 变更名：`lowcode-flow-lifecycle-sync`
> 状态：`implemented`（新版应用增量自动化通过，真实撤回与历史补偿待人工验收）
> 创建日期：2026-09-19

## 1. 问题与根因

低代码单据与 Flowable 流程之间同时维护业务记录状态、流程关联状态和当前待办。现有实现存在四类不一致：

1. 普通“驳回”依赖 BPMN 的驳回分支，“驳回至发起人”虽然写入了 `rejectToStart` 变量，但没有独立路由；当普通驳回策略为“结束”时，两个动作都会走结束分支。
2. `TASK_CREATED/TASK_COMPLETED` 回调会尝试写 `NEED_MODIFY`，但待办动作接口随后又无条件把运行态改回 `IN_PROCESS`，形成时序覆盖。
3. `NEED_MODIFY` 没有被所有运行态判断统一识别，导致批量运行态查询不加载发起人修改待办，单据页拿不到“修改后重提”。
4. 发起按钮只屏蔽部分运行态，终态以及待修改态仍可能因历史配置的 `allowStartFlow` 重新出现；撤回后的 `CANCELED` 也缺少前后端一致兜底。

## 2. 目标

1. 明确区分两个驳回动作：普通驳回按流程级驳回策略执行；“驳回至发起人”进入专用发起人修改回路。
2. 驳回到发起人后，流程实例保持运行，关联状态和单据状态均为 `NEED_MODIFY`。
3. 发起人在低代码列表可编辑原单据，并通过原修改待办“修改后重提”；不得另起新流程。
4. 重提后状态恢复为 `IN_PROCESS`，流程继续原实例和原审批轨迹。
5. 流程通过、驳回结束、撤回后分别同步为 `APPROVED`、`REJECTED`、`CANCELED`。
6. 单据存在任一主流程实例后，不再显示“发起流程”；本轮不提供重复发起新轮次入口。
7. 任务事件重复、乱序或延迟到达时，状态更新保持幂等，终态不被运行态回调覆盖。
8. 应用级流程已成功、已撤回或仍在运行时，同一 `processCode` 的静态“发起流程”不再显示；其他从未发起的并行流程不受影响。
9. 发起应用级流程、发起主流程、修改后重提和撤回期间显示明确的页面 loading 文案，防止用户重复操作。

## 3. 状态机

| 当前状态 | 动作/事件 | 目标状态 | 页面动作 |
| --- | --- | --- | --- |
| `DRAFT` | 发起流程 | `IN_PROCESS` | 查看流程、发起人可撤回 |
| `IN_PROCESS` | 普通驳回且路由到结束 | `REJECTED` | 只读查看流程 |
| `IN_PROCESS` | 普通驳回且路由到发起人 / 驳回至发起人 | `NEED_MODIFY` | 编辑、修改后重提 |
| `NEED_MODIFY` | 修改后重提 | `IN_PROCESS` | 查看流程、继续审批 |
| `IN_PROCESS` / `NEED_MODIFY` | 撤回 | `CANCELED` | 只读查看流程 |
| `IN_PROCESS` | 全部审批通过 | `APPROVED` | 只读查看流程 |

`NEED_MODIFY` 是流程运行态，不是流程终态。`APPROVED`、`REJECTED`、`CANCELED` 是终态。

## 4. 设计

### 4.1 驳回路由

- 普通驳回设置 `approvalResult=reject`、`rejectToStart=false`，按流程级 `rejectStrategy` 或设计器手工分支流转。
- 驳回至发起人设置 `approvalResult=reject`、`rejectToStart=true`。
- JSON 转 BPMN 时，节点开启 `allowRejectToStart` 后补齐 `${approvalResult == 'reject' && rejectToStart == true}` 专用分支，目标为 `Forge_InitiatorModify`。
- 自动生成的普通驳回分支排除 `rejectToStart=true`，避免两个条件同时命中。
- 发起人修改节点完成后沿原流程回到审批节点；直送能力继续复用现有来源节点标记。

### 4.2 状态同步与修复

- `TASK_COMPLETED` 收到驳回动作时先写 `NEED_MODIFY`。
- `TASK_CREATED` 到发起人修改节点时写 `NEED_MODIFY`；进入普通审批节点时修复为 `IN_PROCESS`。
- 待办动作接口在流程仍运行时按动作写中间态：驳回写 `NEED_MODIFY`，通过/退回写 `IN_PROCESS`，不再无条件覆盖。
- 关联表 `flow_status` 与低代码记录的流程状态字段必须同时更新。
- 列表/详情读取当前人的 `Forge_InitiatorModify*` 待办时，即使异步回调尚未完成，也按发起人修改节点提供“修改后重提”。

### 4.3 按钮规则

- `START_FLOW` 只在从未创建主流程实例时显示。
- `START_PROCESS` 按 `processCode` 精确判断：对已运行、成功或撤回的同一应用级流程隐藏，失败可重试的流程保留入口。
- `NEED_MODIFY` 显示“修改后重提”，并保持普通编辑入口可用。
- `APPROVED`、`REJECTED`、`CANCELED` 只保留流程查看/历史能力，不显示“发起流程”。
- 默认单据状态策略中 `REJECTED`、`CANCELED` 不再允许重新发起；已有配置即使仍允许，也由流程实例存在性兜底隐藏。

### 4.4 撤回与操作反馈

- 撤回后单据与流程关联状态统一为 `CANCELED`，该轮流程结束。
- 撤回后隐藏“撤回流程”、“发起流程”和“修改后重提”，仅保留查看详情与审批历史。
- 撤回确认文案明确说明其为终态，不再暗示可修改后重新发起。
- 流程异步操作使用页面局部遮罩与动态文案：“正在发起流程…”、“正在重新提交审批…”、“正在撤回流程…”。

## 5. 非目标

- 不修改业务表结构或新增 Flyway 脚本。
- 不改变指定历史节点“退回”的现有语义。
- 不为终态单据新增“重新开启/新一轮审批”功能；如后续需要，应设计独立动作和权限，而不是复用“发起流程”。
- 不覆盖用户已保存的 BPMN 节点表单、字段权限和审批人配置。

## 6. 验收标准

- [x] 普通驳回在 `TO_END` 策略下结束流程并写 `REJECTED`。
- [x] 同一节点点击“驳回至发起人”时进入发起人修改节点，不受普通驳回结束策略影响。
- [x] 发起人修改待办生成后，关联状态和低代码记录状态均为 `NEED_MODIFY`。
- [x] 单据列表可编辑待修改单据，并展示“修改后重提”，不展示“发起流程”。
- [x] 修改后重提沿原流程实例继续，状态恢复 `IN_PROCESS`。
- [x] 审批完成后状态为 `APPROVED`，不展示“发起流程”。
- [x] 撤回后状态为 `CANCELED`，不展示“发起流程”。
- [x] 应用级流程完成或撤回后，同 `processCode` 的“发起流程”不展示，其他未发起流程仍展示。
- [x] 撤回确认文案与 `CANCELED` 终态语义一致。
- [x] 发起、重提和撤回请求期间有持续可见的 loading 反馈。
- [x] 定向前后端测试、编译/构建和静态检查通过，或明确记录环境限制。

## 7. 2026-09-20 新版应用增量

- 新版应用不再依赖“单据模式”。`documentEnabled=false` 时仍依据实际流程关联、运行状态、发起人和撤回接口权限返回 `WITHDRAW_FLOW`，不要求用户补旧配置；旧配置仍兼容。
- 已确认异步撤回回调在动态仓储填充 `update_by` 时直接读取 Web Session，导致状态回写失败并标记事务回滚。后台无会话时不伪造管理员/发起人身份，保留系统审计语义；租户条件、数据权限和真实 Web/显式执行身份保持原有校验。
- 状态回写异常必须传播，不能吞掉异常后继续更新关联表制造成功假象。
- 编辑/详情的记录请求与流程运行态请求并行，运行态请求序号隔离旧响应；不缓存权限或状态。加载入口抽入同域 composable，不继续堆积 SFC 逻辑。
- 风险标记：涉及状态回写和撤回权限，需人工验收；不改变 `CANCELED` 终态，不新增重新发起能力、不放宽接口权限、不执行历史业务数据修复。已漂移的旧数据需受控补偿，重启不会自动重放旧事件。
