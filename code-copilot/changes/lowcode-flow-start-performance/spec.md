# 低代码流程发起性能优化 Spec

> 变更名：`lowcode-flow-start-performance`
> 状态：`completed`
> 创建日期：2026-09-20

## 1. 问题与根因

低代码列表发起主流程或应用级流程时，用户等待时间由两段叠加：

1. 主请求前会读取发起配置，Flow 服务每次都重新解析 BPMN XML、扫描首个审批节点并执行发起前诊断。
2. 主请求已成功后，`AiCrudPage` 仍串行等待详情运行态刷新和整张列表刷新；列表刷新又会追加一次批量流程运行态查询，导致页面 loading 比真实发起请求更久。

## 2. 目标

1. 发起、修改后重提或撤回接口返回成功后，立即结束页面级 loading 并给出成功反馈。
2. 使用接口返回的 `BusinessFlowRuntimeVO` 立即更新当前行和当前详情运行态，防止成功后短暂继续显示可重复操作的按钮。
3. 整表数据与运行态校准改为后台异步刷新，不再阻塞主操作的 loading。
4. Flow 服务对未变更的流程模型复用发起配置解析结果，避免重复解析 BPMN XML。
5. 缓存必须按租户隔离，模型 XML、版本或更新时间变化后必须立即重建，返回给调用方的可变对象不得污染缓存。

## 3. 设计

### 3.1 前端成功快照与后台校准

- 将流程接口返回的运行态合并到当前行的 `_documentRuntime` 和 `_runtimeActions`。
- 详情/编辑弹窗处于当前记录时，同步更新 `detailRuntime` 和 `formData` 快照。
- 使用可取消的宏任务调度 `loadList()`，确保当前操作的 `finally` 先关闭页面 loading，再进入列表区域 loading。
- 后台刷新失败仅记录警告，不把已经成功的发起/重提/撤回误报为失败。
- 组件卸载时清理尚未执行的刷新计时器。

### 3.2 Flow 发起配置缓存

- 缓存键使用 `tenantId + modelKey`，租户间不共享。
- 缓存项保存模型指纹、发起配置快照和过期时间；指纹覆盖模型 ID、版本、更新时间与 BPMN XML。
- TTL 为 30 秒，最多保留 512 个模型项；达到上限时先清理过期项，再淘汰一个已有项。
- 每次仍先按租户读取模型元数据，指纹不一致时忽略旧缓存立即重新解析，避免流程设计更新后读到旧节点配置。
- 缓存写入和返回均使用深拷贝，防止 Controller 序列化或调用方修改列表后污染后续请求。

## 4. 非目标

- 本轮不修改数据库结构、流程状态机或 BPMN 路由语义。
- 本轮不将 `TASK_CREATED` 待办镜像整体异步化，以免发起成功后立即查不到待办。
- 组织、角色、区域和直属领导的按需加载属于后续结构性优化，需先有分段耗时数据再扩大改动。

## 5. 验收标准

- [x] 主流程接口成功后，页面 loading 不等待详情和整表刷新。
- [x] 发起成功的当前行立即使用返回运行态隐藏发起入口，后台校准后状态与服务端一致。
- [x] 后台列表刷新失败不会将已成功的流程操作提示为失败。
- [x] 同一租户、同一未变更模型的连续发起配置请求只解析一次 BPMN。
- [x] 模型 BPMN 或版本变更后下一次请求立即重新解析。
- [x] 租户之间不共享发起配置缓存，且修改一次返回对象不影响后续请求。
- [x] 前端定向测试、Flow 插件定向测试/编译、前端构建与 `git diff --check` 通过，或明确记录环境限制。
