## 掘金第 12 篇：开放 API 安全三件套（openapi-security）
文件：`output/掘金-开放接口限流改了阈值却不生效防重放幂等5个坑.md`

### 关键前提（与前几篇不同）
`forge-starter-openapi-security`（446 行/8 类）**是真实跑在生产链路上的**——上层 `forge-plugin-capability-platform` 的开放网关九步编排真实调用（限流→幂等→Schema→执行→审计）。**不是源码推演**，可信度高于 cache/idempotent 那两篇（零业务接入）。

### 5 个坑
1. **`RRateLimiter.trySetRate()` 只在首次生效** → 配置从 20 改 200 不生效（key 不含速率值，已存在则直接返回 false）；且每请求都调一次，多一次 Redis 往返
2. **【最该改】防重放跑在验签之前** → `OpenGatewayAuthenticator.authenticateSignature` 顺序是 ①assertNotReplayed（写 Redis nonce）②查 client ③凭据校验 ④verifySignature。未携带任何有效凭据的伪造请求可灌 nonce（存储 DoS + nonce 抢占）。标准做法是先验签（AWS SigV4/微信支付都如此）
3. **幂等锁三参 tryLock(30s lease) 无 watchdog**（接上一篇 Redisson 文）→ 业务超 30s 锁释放，降级为 DB 唯一约束兜底（业务实际跑两次）
4. **快照反序列化失败被归为 503** → `loadSnapshot` 抛 IllegalStateException(RuntimeException) 被统一 catch 成基础设施故障 → 该 Idempotency-Key **永久 503 不可自愈**
5. **快照写失败返回 503 但业务已执行** → 503 对调用方语义是"可重试" → 重试即重复执行，幂等失效

### 做对的地方（可复用）
- **fail-closed**：Redis 不可用抛 503 绝不放行；业务异常原样上抛、只有基础设施异常才转 503（对比 auth 登录锁的 fail-open）
- `ObjectProvider.getIfAvailable()` 延迟取值
- `unlock` 前 `isHeldByCurrentThread()`
- Idempotency-Key **存 SHA-256 哈希**不存明文
- 清理 Job 挂了 `@JobHandler`（对比 excel 的 cleanupExpiredTasks 无调度）+ 分批 500/最多 200 批
- 网关总开关 `enabled=false` 默认关闭
- 唯一索引 `uk_ai_capability_openapi_idem (tenant_id, client_id, capability_id, idempotency_key_hash, del_flag)`（V1.0.74）
