### 三个结论（已写入长期记忆）
1. **长文停掉**：同一时间、同一账号、同样已验证的数字反差钩子，微头条 13.4% vs 长文 0.67%——**差 20 倍**。26 篇长文没量的变量就是"长文本身"，不是选题/标题/账号。微头条在信息流里正文直铺（决策成本低），长文只有标题+缩略图（需主动点击，技术标题对泛用户无点击冲动）
2. **"同一时间发两条"严重拖累展现**：第 1 条单独发 7981 vs 第 6 条同发 528，**差 15 倍**。账号单时间窗推荐配额有限，两条互抢池子
3. **数字反差型二次验证**：13.4% + 16.7% 稳定；反常识型 4.7%。结论稳定，弃用反常识型

### excel 模块核实结果（4223 行 / 30 类）
行数分布：DynamicExportEngine 803 / ExcelImportServiceImpl 732 / ExcelEnhancedController 228 / GenericRowDataListener 232 / **AsyncExportServiceImpl 178**

### 【核心·高危】@Async 三重叠加失效（不止是自调用）
1. 同类内部调用 `executeExportAsync(...)` = `this.xxx()` → 不走代理
2. 方法是 **`protected`**
3. **方法不在 `AsyncExportService` 接口里** → Spring 默认 JDK 动态代理（类实现了接口）→ 代理对象上根本没有这个方法
→ 三缺一不可，只改"自调用"仍然无效

### 其他新发现
- **测试测不出**：`AsyncExportSecurityContractTest` 直接 `new AsyncExportServiceImpl(failingEngine)`，绕过 Spring 容器无代理 → 测试和生产的坏法一模一样，断言永远通过
- **`cleanupExpiredTasks()` 无任何调度**：全项目只有接口声明 + 实现 + 测试 mock，无 `@Scheduled` → 临时文件 + taskStore 永不清理（磁盘 + 内存双爆）
- `taskStore` 本地 ConcurrentHashMap，注释自认"生产建议用 Redis"；无容量上限
- `downloadFile` 用 `Files.readAllBytes` 返回 byte[] → 大文件 OOM
- **`dataCount` 死字段**：Controller 有 getter，全项目无 setter → 永远 null
- **`MockHttpServletResponse` 死类**：私有静态内部类，注释说"用于捕获输出"，实际用的是 `exportToStream`，从未引用
- `expireTime = now + 24h`；`TEMP_DIR` 硬编码 java.io.tmpdir + static 块创建失败只 warn

### 它做得对的地方（可写进文章的正面素材）
- **安全契约测试**：内部异常（含 jdbc 密码串）不外泄，对外只返回 `PUBLIC_FAILURE_MESSAGE`；`filePath` 用 `@JsonIgnore` 挡住
- **SPI 全可选**：metadataProvider / configProvider / dictValueProvider 均 `@Autowired(required=false)`；所有 Bean 都 `@ConditionalOnMissingBean`

### 修复方案要点
拆到独立 Bean（如 `ExportTaskExecutor`）+ `public` 方法 + 跨 Bean 调用（最推荐）；验证口诀：打线程名，看到 `http-nio-8080-exec-1` 就是没生效
