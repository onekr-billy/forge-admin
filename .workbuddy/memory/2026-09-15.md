## 掘金第 14 篇（系列第 4 篇，兑现预告）
《加了 @Idempotent 还是重复扣款了 3 笔：扒完 1279 行幂等 Starter，我挖出 5 个隐蔽的坑》
- 模块实测：main 1279 行 / test 824 行 / 29 个类
- 5 个坑（全部源码核实）：
  1. `SpelUtil` catch 吞异常返回 null → keyValue="" → 幂等键退化成纯 prefix → 全站共用一把锁
  2. **STRICT 策略 `int expire = annotation.expire();` 是死变量**，锁租期由 `LockProperties.leaseTime=5000ms` 决定；Redisson 传了 leaseTime 就不启动 watchdog → 业务超 5s 锁自动过期 → 幂等失效（这是真实事故：压测 500 并发重复扣款 3 笔）
  3. `RedisResultCacheService` 用 `objectMapper.readValue(json, Object.class)` → 返回 LinkedHashMap → 调用点 checkcast 抛 ClassCastException（首次请求正常、重复请求才炸）
  4. **`TokenRequiredStrategyHandler.extractToken()` 真实 BUG**：`(RequestContextHolder) RequestContextHolder.getRequestAttributes()` 强转类型错误，必然 ClassCastException 被 catch 吞 → token 恒为 null → TOKEN_REQUIRED 模式 100% 抛 TokenInvalidException
  5. Token 的 validate（hasKey+get status）与 consume（put status）非原子，高并发双花 → 需 Lua
- 补充坑：`@Idempotent` 声明 `@Target` 含 TYPE 但切面只有 `@annotation` → 类级注解静默失效（呼应 datascope/tenant 篇的 @within 坑）
- 亮点设计：DefaultIdempotentKeyGenerator 用 TreeMap 递归 canonicalize 保证 JSON 字段顺序无关 + SHA-256；三个策略 catch 分支都 unlock（失败可重试）；handler==null 时 fail-open 放行

## 头条第 24 篇（用户要求"技术类的"）
《加了操作日志后接口慢了10倍，我扒完676行源码才找到原因》
- 素材全部核实：`OperationLogAspect` 676 行、`LogThreadPoolConfig`、`OperationAuditContext`（普通 ThreadLocal）
- 三大发现：
  1. **切点是 `@within(@Controller) || @within(@RestController)`**，不是 `@annotation(@OperationLog)`（后者被注释掉）→ 所有 Controller 方法都进切面
  2. 决定跳过之前已经干了 4 件事（拿 request / 遍历 8 项敏感路径 / 构造 logInfo 填 6 字段 / **`apiConfigManager.getApiConfig()` 查配置**）→ 高频 GET 也在白干活
  3. **线程池默认 core=2 / max=5 / queue=500 + CallerRunsPolicy** → 高峰期队列满 → 业务线程自己写日志 → 正反馈拖垮（这是"下午三点必卡"的直接原因）
- 认可的设计：QUERY 全跳过、URL 后缀自动分类操作类型（/page /list /tree... → QUERY）、8 个敏感凭证路径直接排除、@ApiDecrypt 接口的 @RequestBody 参数替换为 `[DECRYPTED_REQUEST_BODY_OMITTED]`
- 客观不足：traceId 只进 MDC 不进库（OperationLogInfo 无 traceId 字段）、finally 里先 saveLogAsync 再 MDC.remove → 异步线程拿不到 traceId、无日志清理归档策略
