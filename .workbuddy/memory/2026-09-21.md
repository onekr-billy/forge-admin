## 掘金第 10 篇（系列第 10 篇，兑现 config 篇预告）
- 交付 `output/掘金-缓存命中了却报ClassCastException多级缓存的5个静默失效坑.md`（cache 模块 2445 行 main + 7 测试）
- **最值钱的可复用设计**：`ForgeCacheAspect.restoreCachedValue` + `requiresTypeConversion` 递归泛型擦除恢复——按方法声明返回类型 `convertValue` 回炉，递归检查数组/Map/Iterable 元素，`Object.class` 直接跳过，转换失败主动 evict 脏缓存
- **5 个坑**：①`register()` 的 `compatibleDefinition` **10 字段全等**，Redis 里 definitions 是 RMap 无 TTL → 改一行 TTL 配置 = 新实例全站缓存静默穿透 ②`resolveScope` 拿不到登录态返回 empty → 切面 `key.isEmpty()` 无日志直接穿透（定时任务/异步线程 100% 不缓存），`SessionCacheIdentityProvider` 还 catch 吞异常 ③非法策略快照只清本地不清 Redis → **每 30 秒 closeHandle 一次**（policyRefreshSeconds 默认 30），且 `validatePolicy` 无条件要求 `nullTtlSeconds > 0`（cacheNull=false 时设 0 就废）④**`clear()` 是唯一无 try-catch 的入口**（get/put/evict 都有）→ 清空失败 = 脏数据 ⑤`ManagedCacheValue.value` 用 `@JsonTypeInfo(Id.CLASS)` 且 ObjectMapper 无 `BasicPolymorphicTypeValidator` → 改包名全量缓存报废 + 反序列化无白名单
- **做得对**：L1 Caffeine + L2 RMapCache + Pub/Sub 跨实例失效，StatusListener 的 `onUnsubscribe` 注释写明"断开期间靠 L1 TTL 兜底陈旧窗口"；key = scope 前缀 + SHA-256 摘要；`CacheTransactionExecutor.afterCommit` 事务提交后才写缓存（切面 `@Order(LOWEST_PRECEDENCE-100)` 保证在事务外层）；LongAdder 独立计数含 `failures`
- **重要事实**：`@ForgeCacheable` **全项目只有 test 在用，业务代码零接入**（grep 确认）→ 坑都还没在真实流量暴露过，文中已如实说明
