# 同样是接 Flowable，为什么芋道要写一堆代码，这个框架3个注解搞定

> 最近接了个采购审批的需求，我把芋道和 ForgeAdmin 都真实跑了一遍。这篇不吹不黑，就聊聊一个二开人员视角下，两家工作流的差距到底在哪。

---

## 一、先说背景：接工作流为什么是"二开之痛"

做企业项目的都知道，中后台框架选型时用户权限、菜单这些大家都有，**真正拉开差距的是工作流**。

因为工作流是唯一一个"业务代码必须深度参与"的模块：

- 请假、报销、采购、合同……每个业务都要接流程
- 审批中要能看到表单，审批完要能更新业务状态
- 老板今天要三级审批，明天要改两级，后天要加会签

选芋道还是选别的，最后都绕不开一个问题：**业务代码和流程引擎，到底怎么缠在一起的？**

芋道（ruoyi-vue-pro）的 bpm 模块我用了挺久，说实话做得不差——仿钉钉的流程设计器、动态表单、OA 请假的完整示例，在开源圈里算第一梯队。这次需求时间紧，我顺手也把之前一直在用的 ForgeAdmin 跑了一遍，对比之下有些东西值得说说。

> 先放演示地址，文章里说的所有东西都能在线试：http://www.dlforgelab.com:8084/forge/login （账号 `admin` / `123456`）

## 二、接入方式对比：这是差距最大的地方

### 芋道怎么接

芋道 bpm 的常规玩法：业务表单自己建表，然后写一个 XXXProcessListener 或者直接调 BPM 的 API 发起流程，回调里更新业务状态。本质上还是"业务代码去调流程引擎"——发起时组装变量 Map，监听器里解析 businessKey 反查业务表。

示例给得很全，但每个新业务流程都要复制粘贴这一套。业务一多，`RuntimeService`、`TaskService` 的调用就散落在各个 Service 里。

### ForgeAdmin 怎么接

ForgeAdmin 的做法是把流程引擎拆成了独立服务（forge-flow），业务侧只通过 3 个注解声明"我要发流程、我要收结果"：

```java
@FlowBind(modelKey = "purchase_process", businessType = "purchase")
@Service
public class PurchaseService {

    @FlowStart(
        businessKeySpEl = "'purchase:' + #order.id",
        titleSpEl       = "#order.applicantName + ' 的采购申请'",
        variablesSpEl   = "{'amount': #order.amount}"
    )
    public PurchaseOrder submit(PurchaseOrder order) {
        purchaseMapper.insert(order);   // 只写业务逻辑
        return order;                    // 流程发起由切面自动完成
    }

    @FlowCallback(on = {FlowCallback.ON_COMPLETED, FlowCallback.ON_REJECTED})
    public void onResult(FlowEventContext ctx) {
        // 审批通过/驳回，更新业务状态
    }
}
```

注意看 `submit()` 方法里**没有一行 Flowable API**。发起流程是切面在方法执行成功后自动做的，SpEL 表达式直接从业务对象里取值，不用手动拼 Map。

引擎和业务通过 HTTP + 事件回调通信，意味着流程引擎可以独立部署、独立扩容，将来真要换引擎，改的是 FlowClient 而不是全部业务代码。

**这一局的结论：芋道是"文档教你怎么写"，Forge 是"设计上让你不用写"。**

## 三、表单联动：低代码这条腿，芋道没有完全补上

审批流的另一半是表单。审批人打开待办，得能看到单据内容；不同节点看到的字段、能改的字段还不一样。

### 芋道的现状

芋道有动态表单（拖拽设计器），但业务表单和流程的联动需要自己搭桥：业务列表、详情页、发起页面都得自己开发，流程里挂表单的 key 要自己维护。

### ForgeAdmin 的做法：业务应用 → 业务对象 → 表单资产，一路级联

![流程设计器中配置业务表单](../images/流程设计.png)

在流程设计器里配全局表单时，是级联选择的：先选业务应用，再选应用下的业务对象，最后选这个应用里实际配置的表单资产。选完之后 `formJson` 里保存的是完整的引用链——应用、对象、表单、页面 ID 全都持久化，不会出现"应用 A 的对象配了应用 B 的表单"这种脏数据。

更关键的是**节点级字段权限**：

![节点表单与字段权限配置](../images/业务流程画布.png)

每个审批节点可以单独配字段权限——可见、可编辑、必填、只读。比如采购审批：

- 直属主管节点：能看到全部字段，只能填审批意见
- 财务节点：金额、预算科目可编辑，其他只读
- 老板节点：只看摘要和总额

而且后端在保存时会**再按节点权限过滤一次字段**，前端隐藏字段只是体验优化，不是安全边界。这个细节很多商用工作流都没做对。

### 发起测试也省了

"发起测试"按钮会按表单类型自动渲染——动态表单用渲染器，业务表单调 AiForm，外置表单按 formUrl 加载，无表单直接空变量发起。**不用先写代码就能验证流程画得对不对**，这个对交付节奏帮助很大。

## 四、审批动作：9 种动作 + 完整状态机

| 能力 | 芋道 | ForgeAdmin |
|------|------|------------|
| 通过/驳回 | ✅ | ✅ |
| 驳回至发起人 | ✅ | ✅（且支持"修改后直送原驳回节点"） |
| 退回指定历史节点 | 部分 | ✅ 流程级配置，多级退回 |
| 委派/改派 | ✅ | ✅ |
| 发起人撤回 | ✅ | ✅ |
| 终结流程 | - | ✅ terminate |
| 签收（候选任务池） | - | ✅ claim |
| 会签（多实例） | 需要懂 BPMN | ✅ 设计器直接配 |
| 发起人自选审批人 | - | ✅ 带启动变量协议和服务端校验 |

![流程时间轴](../images/流程时间轴.png)

细节说一个：**驳回至发起人**这个场景。很多框架做成了"驳回就结束流程"，发起人只能重新发起一遍。Forge 保存了 `FLOW_RETURN_SOURCE_ACTIVITY_ID` 这些变量，发起人改完单据可以正常走完流程，也可以**直接送回原来驳回他的那个节点**。这是真实企业里用得最多、但开源框架最少做对的一个动作。

业务状态和流程状态也不是靠一个"流程结束"事件硬同步的，而是拆成 TASK_CREATED / TASK_COMPLETED / ON_COMPLETED / ON_REJECTED / ON_CANCELED 分别处理，流程实例关联表里还存了 `variables_snapshot` 快照——待办列表不用再去实时读流程变量。

## 五、通知触达：审批流不是站内喊一嗓子就完了

这是最近才补齐的一块，也是我觉得比芋道走得远的地方——**通知矩阵**。

待办、审批结果、抄送三类事件 × 站内信、邮件、短信、企业微信多渠道，在流程模型里用矩阵勾选就行：

- 待办事件：站内信默认开启且不可关（保底）
- 结果通知：可以加邮件、企微
- 抄送：可以推企微卡片
- 短信选了会有资费提示，防止误烧钱

配合之前说的企业协同层，**审批待办可以直接推成企微卡片，老板在手机上点了卡片就能审批**——点卡片时 Forge 会重新校验外部身份 → 接收人 → 租户 → 任务状态 → 办理权限，任务已失效就返回业务失效并同步更新卡片，不会出现"卡片还能点但流程早结束了"的越权操作。

芋道的消息通知要走消息模块自己编排，能做到，但每个流程都要配一遍。Forge 是模型级配置，一次勾选，全渠道生效。

## 六、性能与安全：这些是二开企业绕不开的

### 待办列表的 N+1 问题

大部分开源工作流的待办列表都是这么写的：分页查任务 → 循环查用户姓名 → 循环读流程变量 → 循环查业务单据。任务一多，一个页面几十上百条 SQL。

Forge 的做法是一次 SQL 关联用户、租户、流程模型、分类表，业务摘要走 `FlowBusinessListDisplayAdapter` SPI **按业务对象批量**取数（一个 `XxxFlowListDisplayAdapter` 组件就给待办列表加上合同编号、金额等业务字段），再加三条联合索引兜底。模板数据从 `variables_snapshot` 快照批量恢复，不再逐条调 `getVariable`。

### 多租户与幂等

- 所有流程列表 SQL 显式带 `tenant_id`，候选组匹配同时校验当前租户、有效角色、当前组织
- 审批请求强制幂等键（`idempotencyKey` + `requestDigest`），重复点击、网络重试不会重复审批
- 审批人身份**服务端重新校验**，前端传的 userId 一律不信任
- 索引变更全部走 Flyway 迁移脚本，可回溯

这些单拎出来都不难，难的是每一条都做在框架层，二开的人不用自己操心。

## 七、算账：一个采购审批，两种成本

按一个二开人员接一个新业务流程估算：

| 工作项 | 芋道路线 | ForgeAdmin 路线 |
|--------|---------|-----------------|
| 业务建表 + CRUD | 1 天（代码生成器） | 1 天（AI 生成器） |
| 流程模型设计 | 0.5 天 | 0.5 天 |
| 业务与流程桥接（发起/回调） | 1~2 天 | 0.5 天（3 注解） |
| 审批表单 + 节点字段权限 | 2~3 天（自己开发详情页） | 0.5 天（设计器配置） |
| 待办列表业务摘要 | 1 天 | 0.5 天（Adapter 组件） |
| 通知（邮件/企微） | 1~2 天 | 0.2 天（矩阵勾选） |
| 幂等/租户/安全加固 | 看良心 | 框架层内置 |
| **合计** | **6~10 天** | **3 天左右** |

一个流程省 3~7 天，企业里一年接 10 个流程就是一个月人力。**更值钱的是省掉的那部分都是"容易出线上事故"的部分**——幂等、越权、N+1 恰恰是加班到半夜的常客。

## 八、客观说不足

不吹不黑，说几个真实的短处：

1. **生态和社区不如芋道**。芋道用户基数大，遇到问题搜一搜基本都有人踩过坑；Forge 的问题目前主要靠自己看源码和文档。
2. **候选人任务池（/candidate）还有优化空间**。待办/已办/我发起的已经做了 SQL 关联优化，但候选任务量大时还保留着兼容查询逻辑，官方也明确说了是下一轮优化对象。
3. **业务表单的字段目录兼容成本**。为了同时兼容 fieldCatalog、fields、schema.components 好几种结构，渲染层的分支逻辑不少，二开自定义表单资产时需要理解这套协议。
4. **文档在追，但代码跑得更快**。最近一个月流程模块连做了通知矩阵、多级退回、性能优化好几轮，文档节奏有点跟不上。

这些是"发展中框架"的典型问题，不是设计缺陷。但如果你要的是"开箱即用零学习成本"，芋道的成熟度确实更高。

## 九、什么人适合选它

- **接私活/小团队交付**：审批类需求从设计到交付 3 天，报价空间直接多出来
- **做 SaaS / 多租户产品的**：租户隔离、幂等、越权校验都在框架层，不用自己填坑
- **业务流程会频繁变的**：审批链路、字段权限、通知渠道全在后台配，改流程不用动代码
- **想让审批走出站内的**：企微卡片审批 + 多渠道通知矩阵，是现成能力不是集成项目

如果你的场景是"一个单体项目、一条固定流程、永不变更"，那芋道甚至若依都够用，没必要折腾。
